# MediAgent System Monitoring

This document describes the health monitoring, logging, and observability
features implemented in Task 10.

## Health Monitoring Endpoints

### GET /api/health

Overall health check. Always public (no authentication required).

**Response:**
```json
{
  "status": "HEALTHY",
  "timestamp": "2026-11-27T14:26:00.035Z",
  "uptime": 2,
  "environment": "development",
  "checks": {
    "backend": {
      "status": "HEALTHY",
      "detail": "Express API accepting requests"
    },
    "database": {
      "status": "HEALTHY",
      "detail": "SQLite database connection verified"
    }
  },
  "correlationId": "req-abc123"
}
```

**Status values:**
- `HEALTHY` — All checks passed
- `DEGRADED` — Some checks failed but service is operational
- `UNAVAILABLE` — Service is not operational

**Checks:**
| Check | What it verifies | Failure impact |
|-------|-----------------|----------------|
| backend | Express HTTP server is accepting requests | Service unavailable |
| database | SQLite `SELECT 1` query succeeds | Data operations unavailable |

### GET /api/health/ready

Readiness probe for container orchestrators (Kubernetes, Render, etc.).
Returns HTTP 200 when ready, HTTP 503 when not ready.

**Checks:**
| Check | What it verifies |
|-------|-----------------|
| database | SQLite connection works |
| python-ml | Python executable is available |
| model-artifacts | Diabetes model artifact file exists |

### GET /api/health/models

ML model availability and version tracking. Lists all supported diseases
with their status, version, and artifact presence.

**Response:**
```json
{
  "success": true,
  "summary": {
    "total_models": 5,
    "available_models": 4,
    "unavailable_models": 1
  },
  "models": {
    "diabetes": {
      "status": "TRAINED",
      "readiness": "VERIFIED",
      "model_version": "v2.0.0-pima-diabetes",
      "artifact_present": true,
      "metrics": { ... }
    },
    "typhoid": {
      "status": "NOT_TRAINED",
      "readiness": "UNAVAILABLE",
      "artifact_present": false
    }
  },
  "correlationId": "req-abc123"
}
```

## Structured Logging

### Format

All backend logs are newline-delimited JSON (NDJSON) on stdout/stderr:

```json
{
  "timestamp": "2026-11-27T14:26:00.034Z",
  "level": "info",
  "message": "GET /api/health",
  "service": "mediagent-backend",
  "environment": "development",
  "correlationId": "req-abc123",
  "meta": {
    "ip": "127.0.0.1",
    "userAgent": "curl/7.88.1"
  }
}
```

### Log Levels

| Level | Usage | Environment variable |
|-------|-------|---------------------|
| error | Errors and exceptions | `LOG_LEVEL=error` |
| warn | Warnings and fallbacks | `LOG_LEVEL=warn` |
| info | General operational info | `LOG_LEVEL=info` (default) |
| debug | Debug-level detail | `LOG_LEVEL=debug` |
| silent | No logging | `LOG_LEVEL=silent` |

### PII Redaction

The logger automatically redacts:
- Email addresses → `[REDACTED_EMAIL]`
- Bearer/basic tokens → `[REDACTED_TOKEN]`
- Long hex/base64 strings → `[REDACTED_TOKEN]`
- Object keys containing: email, password, token, secret, api_key, authorization, cookie

**Never log:** patient names, phone numbers, addresses, lab values, or any PII.
Only opaque identifiers (patientId, reportId, correlationId, requestId) are logged.

## Request Correlation

Every HTTP request receives a correlation ID:

1. Client sends `X-Correlation-ID` header (optional, max 128 chars)
2. Server generates one if not provided (`req-<hex>`)
3. Server echoes it back in `X-Correlation-ID` response header
4. ID is attached to `req.correlationId` and `req.log`
5. ID appears in all log entries and error responses for that request

This enables end-to-end request tracing across backend, Python ML service,
and logs without exposing patient-identifiable information.

## System Status Endpoint

### GET /api/system/status

Protected endpoint returning detailed component status:

| Component | Status values |
|-----------|--------------|
| Express Backend API | ONLINE |
| SQLite Database | ONLINE / UNAVAILABLE |
| OCR Engine (Tesseract) | ONLINE / UNAVAILABLE |
| PDF Text Extraction | ONLINE / UNAVAILABLE |
| ML Model (Pima Diabetes) | ONLINE / UNAVAILABLE |
| RAG Knowledge Base | ONLINE / UNAVAILABLE |
| LLM Reasoning Provider | CONFIGURED / UNAVAILABLE |

This endpoint requires authentication. It never exposes static "Online" claims
— every check performs a real verification.

## Monitoring Integration

The structured JSON log format is compatible with:
- Datadog
- Logtail
- CloudWatch Logs
- Elasticsearch / ELK stack
- Any NDJSON-compatible log collector

## Alerts

Emergency alerts are generated by the clinical risk engine
(`server/risk/riskEngine.js`) and are independent of model availability.
Alerts are based on clinical rules, not ML predictions.

## What Is NOT Monitored

- Real-time patient vitals (not part of MediAgent scope)
- Model drift over time (metrics are point-in-time)
- Frontend performance metrics (client-side only)
- User session duration
